# Decisions log

One dated entry per significant decision: what was decided, alternatives considered, why. Read this before assuming why the codebase looks a certain way -- especially if it looks like it disagrees with `PG_PLATFORM_TECHNICAL_PLAN.md`; this file wins when they differ, and should say why.

---

## 2026-09-01 -- ADR-0001: Modular monolith, not microservices

**Decision**: One Spring Boot deployable, package-per-domain (`com.pgplatform.auth`, `.owner`, `.billing`, ...).
**Alternatives considered**: microservices per domain.
**Why**: at pilot scale, microservices add deployment/ops complexity (service discovery, distributed transactions for e.g. "booking + payment") without a matching benefit. Package boundaries already give the option to split a specific module into its own service later if it needs independent scaling. Matches technical plan §7 item 2.

## 2026-09-01 -- ADR-0002: Soft delete + audit as a shared base entity

**Decision**: every JPA entity extends `common.BaseEntity` (`id`, `createdAt`, `updatedAt`, `createdBy`, `updatedBy`, `deletedAt`). Nothing is hard-deleted by application code; "delete" endpoints call `markDeleted()`, persisted as an UPDATE.
**Why**: technical plan §7 item 5 -- decide this pattern once, in Phase 0/1, not per-table later. Also gives every table the audit trail needed for §8's structured-audit-logging recommendation.

## 2026-09-01 -- ADR-0003: Authorization enforced explicitly in the service layer (`OwnershipGuard`)

**Decision**: no Postgres RLS. Every owner-scoped service method calls `OwnershipGuard.requireOwns(...)` against the authenticated principal before reading or mutating.
**Alternatives considered**: Hibernate filters (considered more implicit/easier to forget to apply on a new query); a custom Spring Data `Specification` auto-injected per repository (more infrastructure than needed at this stage).
**Why**: technical plan §7 item 6 -- this is the single highest-value security pattern in the codebase precisely because it's easy to forget on a new endpoint. Explicit calls + a required test per check (`OwnershipGuardIntegrationTest`) make the omission visible in review rather than silent.

## 2026-09-01 -- ADR-0004: JWT access token + opaque, hashed, rotating refresh token

**Decision**: access tokens are short-lived signed JWTs (15 min). Refresh tokens are random opaque strings; only their SHA-256 hash is stored (`refresh_tokens` table), and every `/auth/refresh` call revokes the old one and issues a new one (rotation).
**Alternatives considered**: refresh-as-JWT-too (rejected: revoking a single JWT refresh token needs a blocklist anyway, so an opaque+hashed token is simpler and equally revocable); long-lived access tokens with no refresh (rejected: bigger blast radius if an access token leaks).

## 2026-09-01 -- ADR-0005: Bed auto-creation and resize semantics

**Decision**: creating a Room with `sharingCount = N` creates N `Bed` rows (`Bed 1`..`Bed N`). Changing `sharingCount` later grows by appending new `AVAILABLE` beds, or shrinks by soft-deleting the *highest-numbered AVAILABLE* beds first; shrinking below the number of currently-`OCCUPIED` beds is rejected (409).
**Why**: matches "bed auto-creation from room 'sharing' count, as the prototype does" (technical plan §6 Phase 2) plus the obvious real-world constraint that an occupied bed can't just disappear. See `RoomService.syncBedsToSharingCount` and `RoomBedAutoCreationTest`.

## 2026-09-02 -- ADR-0006: Bed assignment lives in StudentService, not BedService

**Decision**: `Bed.status` is flipped to `OCCUPIED`/`AVAILABLE` only through `StudentService.assignBed`/`moveOut`/`delete` (until Phase 11 booking exists) -- `BedController`'s direct `PATCH /owner/beds/{bedId}/status` still exists (useful for e.g. marking a bed under `MAINTENANCE`) but owners should not use it to fake an assignment, since it doesn't create/update a `Student` record.
**Why**: keeps "who is in this bed" derivable from one place (`students` table) instead of two systems of record that can drift. A DB-level partial unique index (`uq_students_active_bed`) backs this up regardless of which path is used.

## 2026-09-02 -- Deferred: available-bed lookup has no dedicated endpoint

**Status**: the Flutter "assign a bed" picker (`StudentRepository.listAvailableBeds`) composes the existing Floor-list + Room-list-per-floor endpoints client-side and filters for `AVAILABLE` beds, rather than the backend exposing `GET /owner/pgs/{pgId}/available-beds` directly. Fine at today's scale (a PG has a handful of floors); revisit with a real backend endpoint (and probably a search/filter) once a PG with many floors/rooms makes the N+1-ish client-side walk slow, or once Phase 9 (student discovery) needs the same "available beds in a PG" query server-side anyway.

## 2026-09-02 -- ADR-0007: Fee status is stored and recomputed; "overdue" is derived, never stored

**Decision**: `Fee.status` (`PENDING`/`PARTIALLY_PAID`/`PAID`) is a real column, recomputed by `FeeService` from the sum of a fee's `payments` every time one is recorded. Whether a fee is "overdue" is *not* a column at all -- `FeeResponse.from` computes it at read time from `dueDate` vs. today, only when `status != PAID`.
**Alternatives considered**: storing `OVERDUE` as a fourth status value, flipped by a scheduled job once `dueDate` passes.
**Why**: a stored `OVERDUE` status needs something to flip it (a cron job that doesn't exist yet, or a check on every read anyway) and can drift out of sync between the job's last run and now. Computing it at read time is always correct and needs no scheduler -- the tradeoff is it can't be queried/filtered on in SQL directly; if "list all overdue fees" becomes a real feature (e.g. for a reminders/notifications phase), add a computed/indexed expression then rather than pre-emptively.

## 2026-09-02 -- ADR-0008: `fees.pg_id` is denormalized off `student.pg_id`

**Decision**: `Fee` has its own `pg` reference rather than only reaching the PG through `fee.student.pg`.
**Why**: `/owner/pgs/{pgId}/fees` and the dashboard's pending-dues/collected-this-month sums (`FeeRepository`) need to filter/join by PG directly; going through `students` on every query is an avoidable join at this scale. **Cost, spelled out so it isn't rediscovered the hard way**: if a "transfer a student to a different PG" feature is ever built, it must update `fees.pg_id` for that student's existing fees too, or PG-scoped fee lists/sums will silently miss or misattribute rows. No such transfer feature exists today.

## 2026-09-02 -- Deferred: Razorpay / online payments

**Status**: `PaymentMethod` and `Payment` only support offline recording (cash/UPI/bank transfer/card entered by the owner after the fact). Online payment (Razorpay checkout + webhook) is Phase 12 in the technical plan and depends on booking (Phase 11) existing first, since a booking is what a payment attaches to in the original spec -- for now, a `Payment` attaches to a `Fee`, which is a reasonable target for Razorpay too, but revisit this table's shape (idempotency key, gateway order id, unique constraint per §7 item 4) when that phase starts rather than assuming today's four offline-only columns are sufficient.

## 2026-09-02 -- ADR-0009: Complaints are owner-logged only; student self-service is deferred

**Decision**: `POST /owner/students/{studentId}/complaints` is filed *by the owner, on a student's behalf* -- there is no `POST /student/complaints` a logged-in Student user can call for themselves.
**Why**: a `Student` (the record created in Phase 4) is data the owner manages, not tied to a `users` login row -- see the Student entity's own javadoc and the "student is NOT a login" note from Phase 4. A logged-in Student `User` has no linkage today to *which* `Student` record is theirs, so there's nothing to authorize a self-service complaint against. Building that linkage properly is really part of Phase 11 (student registration/booking), where a Student login needs to attach to a Student record anyway for booking to make sense. Revisit complaint filing at that point rather than bolting on a partial linkage now.
**Consequence for Phase 9-11 implementers**: when the Student-login-to-Student-record link is built, add `POST /student/complaints` reusing `Complaint`/`ComplaintService` (just a different, self-scoped authorization path -- "this student can only file/view their own complaints" mirroring `OwnershipGuard`'s owner-side pattern) rather than a parallel complaint system.

## 2026-09-02 -- ADR-0010: Complaint status changes maintain `resolvedAt` automatically; resolving requires notes

**Decision**: `resolvedAt` is set to "now" whenever `status` moves into `RESOLVED` or `CLOSED`, and cleared (`null`) if moved back to `OPEN`/`IN_PROGRESS` -- the client never sets it directly. Moving to `RESOLVED` without `resolutionNotes` is rejected (409).
**Why**: mirrors the "derived, not client-supplied" pattern already used for `Fee.overdue` (ADR-0007) and keeps a record of *why* something was resolved, which matters for a complaint just as much as it does for a payment.

## 2026-09-02 -- ADR-0011: Receipts are snapshot-based, one per payment, numbered from a DB sequence

**Decision**: `Receipt` copies `studentNameSnapshot`, `pgNameSnapshot`, `feePeriodMonth`, `feePeriodYear` at issue time instead of only holding FKs and joining live. `Receipt.receiptNumber` (`RCPT-<year>-<6-digit seq>`) is drawn from a Postgres sequence (`receipt_number_seq`) via `nextval(...)`, not computed in Java. Exactly one `Receipt` is generated per `Payment` (unique FK), from inside `FeeService.recordPayment`, never via a client-facing `POST`.
**Alternatives considered**: a plain FK-only receipt that joins `Student`/`Pg`/`Fee` at read time; a Java-side counter (e.g. `count(*) + 1`) for the sequence number.
**Why**: a receipt is a legal/financial document -- what it displayed the day it was issued has to stay stable even if the student is later renamed, moved to a different PG, or the fee is edited, so a live join is wrong here in a way it isn't for `Fee`/`Complaint`. A DB sequence avoids the race a Java-side counter would have under concurrent payments (two owners recording payments at the same instant could otherwise compute the same "next" number); `nextval()` is atomic at the database level for free.
**Consequence**: `Receipt` rows will drift from the current `Student`/`Pg` name if those are edited later -- that's intentional, not a bug to fix.

## 2026-09-02 -- ADR-0012: Document storage is stubbed pending real object-storage credentials

**Decision**: `DocumentStorageGateway` (store/generateSignedUrl/delete) has one implementation today, `StubDocumentStorageGateway`, and every method throws `UnsupportedOperationException` -> mapped by `GlobalExceptionHandler` to `501 Not Implemented`. `DocumentService.upload` calls the gateway **before** persisting a `Document` row, so a 501 never leaves orphan metadata with no backing file. The `documents` table (V8) and full CRUD contract exist now regardless.
**Alternatives considered**: skip building the Documents feature entirely until storage is provisioned; fake a "success" response that silently drops the file.
**Why**: same reasoning as Google OAuth in Phase 1 -- exposing the real API contract now lets the Flutter/web clients (and this backend's own tests) be built against a stable shape, rather than blocking on infrastructure that isn't this repo's to provision. A silent fake-success path would be worse than an honest 501: it would look like it worked and then lose the file.
**What's needed to finish this end-to-end**: an S3-compatible bucket (AWS S3, Cloudflare R2, or MinIO for local dev) plus access key/secret/bucket name/region, wired into `application-dev.yml` (`infra/.env.example` already has placeholders). Once available, `StubDocumentStorageGateway` gets replaced by a real implementation (e.g. `S3DocumentStorageGateway`) behind the same interface -- no controller/service/DTO changes needed. No Flutter upload screen was built yet either, for the same reason (see `docs/requirements.md`) -- deliberately deferred rather than building UI against an endpoint that always fails.

## 2026-09-02 -- ADR-0013: Reports are computed at read time, not stored or scheduled

**Decision**: Phase 8's revenue/occupancy/outstanding-dues reports (`ReportService`) all derive their numbers directly from `Fee`/`Payment`/`Expense`/`Bed` rows on every request. There is no reporting table, no nightly aggregation job, and no cache.
**Alternatives considered**: a scheduled job that pre-computes monthly summaries into a `report_snapshots` table; caching report responses for a few minutes.
**Why**: consistent with the "derived, not stored" pattern already used for `Fee.overdue` (ADR-0007) -- at today's data volume (a handful of PGs, a few hundred fees/payments/expenses per owner) these queries are cheap, and a live number is always correct, with no staleness window and no job to keep running. `revenue` loops one query pair per requested month (default 6, capped at 24) rather than a single grouped SQL query, trading a few extra round-trips for reusing the exact same `FeeRepository`/`ExpenseRepository` sum methods the dashboard already uses -- keeps one source of truth for "how much did we collect between two dates."
**Revisit when**: a PG's fee/payment history grows into the tens of thousands of rows and these queries show up in slow-query logs, or when a report needs to look back further than ~2 years (raise `ReportService.MAX_MONTHS` first; if that's still too slow, that's the signal to add a real aggregation table).

## 2026-09-02 -- ADR-0014: Public discovery search pushes rent filters into the DB query, not Java

**Decision**: `PgRepository.search` filters by city/genderPreference/rent range entirely in one JPQL query (rent range via `EXISTS` subqueries against `Room`), returning a real `Page<Pg>` that a project-wide `PagedResponse<T>` envelope wraps for the controller -- not Spring's `Page`/`PageImpl` directly (their own docs flag those as not a stable JSON contract), and not a "fetch everything, filter/paginate in Java" shortcut.
**Why**: filtering in Java after fetching a page would silently return fewer results than `size` whenever a filtered-out row shared a page with matches, corrupting pagination. Pushing every filter into the query keeps `totalElements`/`totalPages` correct no matter which filters are combined.
**Consequence for future filters**: any new discovery filter (amenities, distance-from-a-point, etc.) needs to join this same pattern -- push it into `PgRepository.search`'s JPQL/EXISTS clauses, don't post-filter the page's content.

## 2026-09-02 -- ADR-0015: Discovery is public/unauthenticated; there is still no booking endpoint

**Decision**: `/public/pgs` and `/public/pgs/{pgId}` require no login at all (technical plan §6 explicitly frames search/PG-details as buildable "as soon as Phase 2's data exists," ahead of booking). Both the Next.js and Flutter details pages tell the student to contact the owner directly rather than offering any booking action.
**Why**: building discovery this way lets it ship well ahead of Phase 11 (booking) without a half-working "book now" button that goes nowhere, and matches the plan's own phase ordering. It also means today's numbers (`availableBeds`, per-room `RoomAvailabilityResponse.availableBeds`) are read-only signals for a browsing student, not a reservation -- nothing stops two students from being told the same bed is free and both contacting the owner about it, since there is no hold/lock concept until Phase 11's concurrency-safe booking exists.
**Consequence for Phase 11 implementers**: the booking flow needs its own concurrency-safe path to claim a bed (this is called out as the explicit acceptance criterion for that phase already) -- it must not simply trust a snapshot read from these discovery endpoints.

## 2026-09-02 -- ADR-0016: Live bed availability uses SSE, PG-level granularity only, in-memory subscriber registry

**Decision**: Phase 10 is implemented with Server-Sent Events (`BedAvailabilityBroadcaster`, one emitter per connected client held in an in-process `ConcurrentHashMap<pgId, List<SseEmitter>>`), not WebSocket and not client-side polling. The pushed event is PG-level (`{pgId, totalBeds, availableBeds}`) -- per-room availability is not pushed live on either client; both the Next.js and Flutter PG-details pages keep showing the per-room numbers from their one-time REST fetch.
**Alternatives considered**: WebSocket (bidirectional, but this feature is one-way server→client only, so the extra complexity buys nothing); client polling every N seconds (simpler but wastes requests when nothing has changed, and has a worse worst-case latency); pushing full per-room payloads on every change.
**Why SSE over WebSocket**: the data flow is strictly one-directional (owner action → student view), which is exactly what SSE is for; it also rides plain HTTP (no separate protocol upgrade to worry about through proxies/load balancers) and browsers auto-reconnect `EventSource` on drop for free -- the Flutter client has to reconnect manually since Dart has no built-in SSE client (see `ApiClient.sseStream`, a small hand-rolled parser rather than a new pub dependency for one consumer).
**Why PG-level, not per-room**: a student watching a PG's details page cares most about "is anything still available," and pushing full per-room diffs is meaningfully more payload/complexity for a v1 pilot's scale. Revisit if per-room live updates become a real ask (e.g. once Phase 11 booking lets a student "hold" a specific bed and needs to see that specific bed flip out from under them live).
**Why an in-memory registry, not Redis pub/sub or similar**: this only works correctly as long as the backend runs as a single instance -- an emitter registered on instance A is invisible to a bed-status change committed via instance B. Fine for a pilot behind one instance; **this is the first thing to revisit if the backend is ever horizontally scaled** (swap to Redis pub/sub or a similar broker so `notifyChanged` fans out across instances).
**Consequence for future bed-status-mutating code**: `BedService.updateStatus`, `RoomService.create/update/delete`, and every bed-status-changing path in `StudentService` (create/assignBed/moveOut/delete) all call `BedAvailabilityBroadcaster.notifyChanged(pgId)` after saving. Any *new* code path that flips `Bed.status` or changes a PG's bed count must call it too, or the live view will silently go stale for that PG until someone reloads.

## 2026-09-02 -- ADR-0017: Booking concurrency is enforced with a pessimistic row lock, not optimistic locking or a bulk compare-and-swap

**Decision**: `BookingService.book` takes a Postgres row lock on the target bed (`BedRepository.findByIdForUpdate`, `SELECT ... FOR UPDATE` via `@Lock(LockModeType.PESSIMISTIC_WRITE)`) *before* checking `Bed.status == AVAILABLE`, and only releases it when the transaction commits (after the Booking row is inserted and the Bed is saved as `OCCUPIED`). A second concurrent request for the same bed blocks on that lock until the first transaction finishes, then sees the already-`OCCUPIED` status and cleanly fails with `ConflictException` (409) -- it can never observe the pre-update "available" state and race past the check. A partial unique index (`uq_bookings_bed_confirmed`, at most one `CONFIRMED`, non-deleted booking per `bed_id`) exists as defense-in-depth, matching the project's established "DB constraint + proactive check" pattern (`uq_fees_student_period`, `uq_students_active_bed`) -- it is not the primary mechanism.
**Alternatives considered**:
1. **Optimistic locking** (a `@Version` column on `Bed`, retry-on-conflict) -- would work, but this project has never used JPA's `@Version` anywhere else, and a retry loop for a user-facing "book this bed" action has worse UX than "no, that bed just got taken" (the loser should not get a phantom retry that might grab a *different* now-available bed the student never selected).
2. **A bulk `@Modifying` compare-and-swap UPDATE** (`update beds set status='OCCUPIED' where id=:id and status='AVAILABLE'`, check the affected-row count) -- correct and lock-free, but bulk JPQL/native updates bypass Spring Data's `AuditingEntityListener`, so `updated_at`/`updated_by` would silently stop being maintained on this exact code path. Rejected specifically to avoid that inconsistency; the pessimistic-lock approach goes through a normal entity fetch + save, so auditing behaves identically to every other bed-status change in the codebase (`BedService`, `RoomService`, `StudentService`).
3. **Application-level `synchronized`/mutex** -- doesn't work at all once there is more than one backend instance; a DB-level lock is correct regardless of instance count.
**Acceptance test**: `BookingConcurrencyTest.exactlyOneOfTwoSimultaneousBookingsOnTheSameBedSucceeds` -- two real threads, each running `BookingService.book` in its own transaction, released at the same instant via a `CountDownLatch`, against a single bed. Asserts exactly one `BookingResponse` and exactly one `ConflictException`, and that the database ends up with exactly one `CONFIRMED` booking on that bed. This is the explicit "two simulated simultaneous booking requests" acceptance criterion the technical plan calls for in Phase 11 -- not just code review.
**Consequence**: any future code path that changes `Bed.status` around a booking (e.g. an owner manually freeing/occupying a bed that has an active booking) should go through the same `findByIdForUpdate` discipline if it needs to interact safely with a concurrent booking attempt. `BookingService.cancel` already does.

## 2026-09-02 -- ADR-0018: A Student login links to a Student record only through booking; booking ships Flutter-only, not on the web app yet

**Decision**: `students.user_id` (V9 migration, unique, nullable) is the first link ever created between a Student *login* (`users` row, role STUDENT) and a Student *record*. It's populated exactly one way: `BookingService.book`'s `findOrCreateStudentForUser` creates a new Student row (pre-filled from the User's name/phone) the first time that user ever books, or reuses the existing one on a later booking. There is still no path for a Student login to "claim" a pre-existing, owner-added Student record (e.g. one an owner manually entered before that person ever signed up) -- those stay two unrelated rows unless an owner or a future admin tool links them explicitly.
Booking's client-side UI shipped in the Flutter app only (`PgSearchScreen` → `PgDetailsScreen` → book a specific bed chip → `MyBookingsScreen`) -- the Next.js web app's student pages (`/search`, `/pgs/{pgId}`, Phase 9) remain fully unauthenticated and now just display each room's available bed labels informationally, with a note pointing at the mobile app to actually book.
**Why not build web auth too**: the web app has zero auth infrastructure today (no login page, no token storage, no session handling) -- Phase 1's JWT auth was only ever wired into Flutter. Building a parallel web login flow was out of scope for "implement booking" and would have doubled this phase's size for a v1 pilot; the Flutter app already has full Student auth (phone+OTP, Phase 1) to build on.
**Revisit when**: (a) the web app needs its own student auth for some other reason (student self-service complaints, Phase 9's own deferred item, might be the trigger) -- at that point wire booking into the web app too, reusing `BookingService`/`BookingRepository` as-is; (b) an owner needs to link an existing owner-added Student record to a login after the fact -- add an explicit "claim" endpoint rather than silently merging on some heuristic like matching phone numbers.

## 2026-09-02 -- ADR-0019: Razorpay payments -- outbound order creation is stubbed, webhook processing is fully real; a Payment still attaches to a Fee, not a Booking

**Decision**: `RazorpayGateway.createOrder` is stubbed (`StubRazorpayGateway`, always throws `UnsupportedOperationException` -> 501) since no Razorpay account/API keys are provisioned -- same pattern as Google OAuth (Phase 1) and Document storage (Phase 7b). Unlike those two, the *inbound* half of this phase (webhook signature verification, idempotent processing, recording the resulting `Payment`) is fully implemented and tested today, because none of that needs a live Razorpay account -- `RazorpaySignatureVerifierTest` computes signatures the same way Razorpay would, and `PaymentOrderServiceTest` drives `handleWebhookPayload` directly with a manually-inserted `PaymentOrder` standing in for one a real `createOrder` call would have produced.
An online payment still attaches to a **Fee**, not directly to a **Booking** -- this supersedes the tentative note left in the Phase 5 "Deferred: Razorpay / online payments" entry above (which flagged the shape as worth revisiting once real booking existed). Now that Booking (Phase 11) exists: a booking's first month's rent is itself represented as a Fee an owner creates (or, in a future phase, one auto-created at booking time) -- paying "for a booking," in practice, means paying that Fee. Keeping `Payment` attached to `Fee` avoids a second parallel ledger and reuses the existing amountPaid/balance/status machinery (`FeeService`) rather than duplicating it for online payments specifically.
**Idempotency mechanism** (technical plan §7 item 4's concrete ask): `PaymentOrder.idempotencyKey` is client-generated per payment attempt and unique at the DB level (`uq_payment_orders_idempotency_key`) -- `PaymentOrderService.createOrder` checks for an existing order with that key *before* calling the gateway at all, so a client retry after a dropped response never double-charges or creates a duplicate order. On the inbound side, `handleWebhookPayload` checks `PaymentOrder.status == PAID` before doing anything, making webhook redelivery (which Razorpay explicitly says to expect) safe.
**Why call the gateway before persisting anything**: same "no orphan row on failure" discipline as `DocumentService.upload` (Phase 7b) -- `createOrder` calls `razorpayGateway.createOrder(...)` before constructing a `PaymentOrder` row, so today's always-501 failure leaves zero rows behind.
**What's needed to finish this end-to-end**: a Razorpay account plus `RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET`/`RAZORPAY_WEBHOOK_SECRET` (placeholders already in `application.yml`, wired through `RazorpayProperties`). Swap `StubRazorpayGateway` for a real HTTP-calling implementation behind the same `RazorpayGateway` interface -- no controller/service/DTO changes needed, matching the Document-storage precedent.
**Client scope**: same-phase decision as ADR-0018 -- `GET /student/fees` (read-only) shipped on Flutter (`MyFeesScreen`), but no "Pay Online" checkout UI was built anywhere yet, since the endpoint it would call always 501s -- consistent with the earlier decision not to build a Document-upload screen for the same reason. Build it once `StubRazorpayGateway` is replaced with a real implementation.

## 2026-09-02 -- ADR-0020: Notifications go through one NotificationService fan-out; push/email delivery is logged, not sent; no Flutter FCM integration yet

**Decision**: `NotificationGateway` gained `sendPush` alongside the `sendSms`/`sendEmail` it already had (from earlier OTP/password-reset work). `LoggingNotificationGateway` remains the only implementation -- it logs every call instead of delivering anything, same role `StubDocumentStorageGateway`/`StubRazorpayGateway` play for their respective external dependencies, except this one doesn't throw: a notification is a side effect of something that already succeeded (a booking, a payment, a resolved complaint), so "notification delivery isn't wired up" should never surface as an error to the user or fail the underlying operation -- it should just quietly not happen (logged, for whoever's watching logs), which is why `LoggingNotificationGateway` logs rather than throwing `UnsupportedOperationException` the way Document storage and Razorpay do.
A new `NotificationService.notifyUser(userId, title, message)` is the one place calling code should reach for -- it looks up the user's email and every registered `DeviceToken`, calls the gateway for each, and swallows any individual delivery failure (logged, not propagated) so a notification problem can never fail the business operation that triggered it. Wired into four concrete trigger points per the technical plan's instruction to actually connect notifications to real events, not just build an unused capability: booking confirmed (notifies both the student and the PG owner), booking cancelled (notifies the owner), an online payment received via the Razorpay webhook (notifies the student), and a complaint marked `RESOLVED` (notifies the student, only when they have a linked login -- see ADR-0009).
**Push registration exists server-side (`/me/device-tokens`) but no Flutter client calls it.** Real push needs a Firebase (or equivalent) project, its config files wired into the Android/iOS native projects, and the `firebase_messaging` plugin added to `pubspec.yaml` -- none of which exist yet, and none of which can be fabricated without a real Firebase project to point at. Building the registration call without anything to register would just be dead code exercising an endpoint with no real token behind it.
**WhatsApp is explicitly out of scope for this phase** (technical plan: "WhatsApp explicitly deferred to its own later phase given Meta Business API approval lead time") -- not represented anywhere in `NotificationGateway` yet.
**What's needed to finish this end-to-end**: (1) email -- a transactional email provider account (SES/Postmark/Resend) and its API key; (2) push -- a Firebase project, `google-services.json`/`GoogleService-Info.plist` wired into the Flutter app, and the `firebase_messaging` package added, then a real device token flows into `POST /me/device-tokens` the same way it would today. Swap `LoggingNotificationGateway` for a real implementation behind the same `NotificationGateway` interface -- no caller changes needed, same precedent as every other stubbed integration in this project.

## 2026-09-02 -- ADR-0021: Real-time sync extended to all NotificationService events via a per-user SSE stream; piggybacks on Phase 13's fan-out point instead of new per-event infrastructure

**Decision**: Phase 10 built a public, per-PG SSE stream for bed availability (`BedAvailabilityBroadcaster`). Phase 14 generalizes that same pattern -- `ConcurrentHashMap<key, CopyOnWriteArrayList<SseEmitter>>` + `subscribe()`/`publish()` -- to a new `UserEventBroadcaster`, keyed by `userId` instead of `pgId`, exposed as `GET /api/v1/me/events/stream` (authenticated, unlike the public Phase 10 stream).
Rather than adding bespoke SSE publish calls at each of Phase 13's four notification trigger points, `NotificationService.notifyUser` itself now calls `userEventBroadcaster.publish(userId, title, message)` at the end, alongside the existing email/push delivery loop. This means booking confirmed/cancelled, payment received, and complaint resolved all get a live in-app echo automatically, with zero changes to `BookingService`, `PaymentOrderService`, or `ComplaintService` beyond what Phase 13 already wired -- the fan-out point Phase 13 created for push/email turned out to be exactly the right seam for this too.
**Client scope**: Flutter/dio-only (`LiveEventsListener`, a `StatefulWidget` wrapping `StudentHomeScreen` and `PgListScreen`, showing a `SnackBar` per event) -- the browser `EventSource` API cannot set an `Authorization` header, and this endpoint is authenticated (unlike Phase 10's public stream, which browser `EventSource` could and did consume via `LiveAvailabilityBadge`). No workaround (e.g. a short-lived query-string token) was built this phase; the web app gets no live in-app notifications yet.
**Same single-instance caveat as ADR-0016**: `UserEventBroadcaster`'s emitter registry is in-memory per backend instance and won't fan out across horizontally-scaled instances -- a user connected to instance A won't receive an event published by instance B. Flagged as the first thing to revisit if this backend is ever scaled beyond one instance (a shared pub/sub layer -- Redis, or Postgres `LISTEN`/`NOTIFY` -- would be the fix, at that point probably applied to both this stream and the Phase 10 one together).
**No heartbeat on this stream**, unlike `BedAvailabilityBroadcaster` (which schedules a periodic no-op event to keep idle SSE connections alive through proxies/load balancers that time out idle connections). Not yet a known problem, but worth adding the same heartbeat here if long-lived idle connections turn out to get silently dropped in practice.
**What's needed to extend this further**: any future event type just needs to go through `NotificationService.notifyUser` (or a sibling method following the same shape) to automatically get both push/email and this live echo -- no new SSE plumbing required per event type.

## 2026-09-02 -- ADR-0022: Phase 15 security audit findings and fixes -- per-IP auth rate limiting, an idempotency-key cross-student authorization gap, structured access logging for documents/payments, and generic-500 logging

**Context**: Phase 15 (technical plan §6/§7 item 6-7, §8) is a dedicated audit pass, not new features -- reviewing what Phases 1-14 built against the plan's own risk list (row-level authorization without RLS, rate limiting, structured audit logging) rather than assuming it was all covered correctly the first time. This entry records what the audit found and what was changed as a result.

**1. Authorization discipline (§7 item 6) -- audited, found consistent, not changed.** Every owner-scoped service (`PgService`/`FloorService`/`RoomService`/`BedService` via `OwnershipGuard`; `StudentService`/`FeeService`/`ComplaintService`/`DocumentService`/`ReportService` via their own `requireOwned*` helpers following the identical discipline; `BookingService`/`PaymentOrderService` via a student-id-equality check) takes the authenticated principal's id as a parameter and checks it before touching data -- never trusts a client-supplied id for scoping. Confirmed by grep across every service in `backend/src/main/java` -- no owner- or student-scoped read/write was found that skips this. `docs/security.md`'s authorization section is updated below to reflect the pattern as it actually stands today (it previously only named the four original `OwnershipGuard` consumers from Phase 2-3 and described later features as "not built yet").

**2. Fixed: idempotency-key cross-student authorization gap in `PaymentOrderService.createOrder`.** `payment_orders.idempotency_key` (V10) is unique *globally*, not per-student. The early-return path for a repeated key (`existing.isPresent()`) returned that order's details without checking it belonged to the calling student -- a client that reused another student's key (by collision, or a low-entropy client bug) would be handed back that student's payment order. Fixed by checking `order.getFee().getStudent().getId().equals(studentId)` on that path too, throwing `ForbiddenException` otherwise. Not exploitable in production today (`createOrder` always throws before reaching persistence, since `RazorpayGateway` is still stubbed -- ADR-0019), but exactly the kind of gap that must be closed before the stub is replaced, not discovered after. Covered by a new test, `reusingAnotherStudentsIdempotencyKeyIsForbiddenRatherThanHandingBackTheirOrder`.

**3. Added: per-IP rate limiting on `/api/v1/auth/**` (technical plan §7 item 7).** `OtpService` already capped OTP requests per phone number (Phase 1), but nothing capped requests per *caller* -- an attacker with one IP could brute-force `/auth/owner/login` passwords, spam `/auth/owner/password-reset/request`, or cycle through many phone numbers to run up SMS costs despite the per-phone cap. `RateLimitFilter` (a new `OncePerRequestFilter`, registered before `JwtAuthFilter` in `SecurityConfig`) caps requests per (client IP, path) to `app.rate-limit.auth.max-requests` (default 20) per `app.rate-limit.auth.window-seconds` (default 60), returning 429 over the limit. Applies only to `/api/v1/auth/**` since everything else is already behind JWT auth, where abuse is attributable to an account rather than an anonymous IP.
Same in-memory-registry, single-instance caveat as `BedAvailabilityBroadcaster` (ADR-0016) and `UserEventBroadcaster` (ADR-0021): counters are a per-instance `ConcurrentHashMap`, so a multi-instance deployment gets roughly `instanceCount x limit` through before every instance's window independently trips -- a weaker limit, not a bypass. Revisit with a shared store (Redis, or a Postgres table) if ever scaled horizontally.
**Trusts `X-Forwarded-For` for the client IP**, which is only safe behind a reverse proxy/load balancer that sets (and never passes through a client-supplied value for) that header. **Phase 16 (pilot deployment) must confirm the chosen reverse proxy is configured this way** before this filter can be relied on in production -- flagged directly in `RateLimitFilter`'s javadoc and in `docs/security.md`.
Test-profile override: `application-test.yml` raises `max-requests` to 100000 so integration tests hitting the same localhost IP/path repeatedly across many `@Test` methods never trip it by accident; `RateLimitFilterTest` exercises the real low limit directly via `ReflectionTestUtils`, independent of that profile.

**4. Added: structured access logging for documents and payments (technical plan §8).** A dedicated `AUDIT.document`/`AUDIT.payment` SLF4J logger (separately routable/retainable from ordinary application logs by name, without new infrastructure) now logs one line per document `downloadUrl`/`delete` call and per successful Razorpay webhook capture -- who (ownerId/studentId), what (documentId/paymentOrderId), when (via the log timestamp). This is a first step -- a searchable structured log line -- not the queryable audit-trail *table* a mature deployment would eventually want; revisit if/when compliance requirements need query-by-student or a retention guarantee stronger than log retention.

**5. Added: unhandled exceptions are now logged server-side.** `GlobalExceptionHandler.handleGeneric`'s client response deliberately never included `ex.getMessage()` or a stack trace (avoids leaking internals, e.g. a raw SQL exception revealing schema), which was correct and unchanged -- but a `@RestControllerAdvice` handler suppresses Spring Boot's own default error logging for exceptions it handles, so every unhandled exception was previously invisible server-side too. Added `log.error(..., ex)` inside the handler so 500s stay debuggable/alertable without changing what the client sees.

**Not changed, flagged as an open item**: Spring Boot is pinned at 3.2.5 (`backend/pom.xml`), released April 2024 -- there have almost certainly been security patch releases on the 3.2.x line since. No dependency version was bumped in this pass: there is no Maven/network access available in this environment to verify a bump doesn't break the build (see the recurring "nothing here has been verified by an actual compiler" caveat throughout this project's history), and shipping an unverified dependency bump would be worse than flagging it. **Action item for the user**: run `mvn versions:display-dependency-updates` (and check Spring's own security advisories) before Phase 16, and upgrade with a real `mvn verify` run backing it up.

## 2026-09-02 -- ADR-0023: Phase 16 deployment prep -- two documented paths (managed PaaS vs. self-hosted Caddy+compose), no infrastructure actually provisioned

**Decision**: Since actual cloud provisioning is the user's decision (which provider, what budget) and not something to do on their behalf, Phase 16 delivers preparation only: `docs/deployment.md` (env var reference, migration/rollback/backup runbook, pre-launch checklist), `backend/src/main/resources/application-prod.yml` (fails fast on a missing `JWT_SECRET` rather than falling back to the dev secret, trusts proxy headers via `forward-headers-strategy: framework`), and `infra/docker-compose.prod.yml` + `infra/Caddyfile.example` for a self-hosted option.
**Why two paths documented rather than one prescribed**: a managed PaaS (Railway/Render/Fly + a managed Postgres + Vercel for the web app) needs close to zero ops work and has usable free/cheap tiers for a pilot, but a self-hosted single VM is a reasonable alternative if the user wants more control or lower long-run cost -- recommending only one would be presuming a decision (budget, ops comfort) that's genuinely the user's to make, consistent with this project's practice of not silently deciding cross-cutting things.
**Why Caddy specifically for the self-hosted path**: automatic Let's Encrypt HTTPS with no manual certbot/cron setup, and -- more load-bearing -- it overwrites `X-Forwarded-For` on every proxied request rather than passing through a client-supplied value, which is exactly the assumption `RateLimitFilter` (Phase 15, ADR-0022) documented as required and unverified. Any managed PaaS in Path A already does the equivalent. This closes the loop on that Phase 15 open item for whichever path gets chosen.
**`application-prod.yml`'s fail-fast `JWT_SECRET`**: `application.yml`'s `${JWT_SECRET:dev-only-secret-change-me-dev-only-secret-change-me}` fallback exists for local dev convenience, but the exact same fallback silently working in a misconfigured production deploy would mean every JWT in production is signed with a secret visible in this public-pattern repo. The `prod` profile overrides it with `${JWT_SECRET}` (no default) so a missing env var is a startup crash, not a silent security hole.
**What's still not done**: no account has been created with any provider named in `docs/deployment.md`; no domain purchased; no backup actually taken or restore actually tested (both called out as explicit pre-launch checklist items, not assumed). This ADR documents preparation, not completion -- the technical plan's 16 phases are now all addressed to the extent buildable without the user's own infrastructure decisions and credentials.
